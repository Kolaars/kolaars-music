# Архитектура

Kolaars Music — обычное Electron-приложение из трёх процессов. Главный процесс отвечает за
файлы, сеть и хранение; интерфейс получает к ним доступ только через узкий мост; общий слой
(`src/shared`) не зависит ни от Node, ни от DOM и используется всеми сторонами.

```
┌──────────────────────────── main (CommonJS) ────────────────────────────┐
│ index.ts   окно, схема kmedia://, CSP, единственный экземпляр           │
│ ipc.ts     все ipcMain.handle — единственная точка входа для интерфейса │
│ db.ts      профили + kolaars.json: атомарная запись + debounce           │
│ media.ts   привилегированная схема kmedia:// со списком путей           │
│ http.ts    fetch с таймаутом, ретраями и LRU-кэшем                       │
│ localFiles.ts + sidecarCover.ts   импорт файлов с диска                   │
│ importList.ts / downloads.ts   список из другого сервиса, офлайн-загрузки │
│ providers/ archive.ts, lyrics.ts   внешние API                          │
│ lyrics/pack.ts   встроенный сборник текстов                             │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │ ipcMain.handle / webContents.send
┌─────────────────────────────────┴───────────────────────────────────────┐
│ preload   window.kolaars — типизированный мост, разворачивает IpcResult  │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │ contextBridge (sandbox, contextIsolation)
┌─────────────────────────────────┴───────────────────────────────────────┐
│ renderer  React 19 + zustand: state/, views/, components/, styles/       │
└─────────────────────────────────────────────────────────────────────────┘
```

## Общий слой (`src/shared`)

| Файл | Содержимое |
| --- | --- |
| `types.ts` | Доменная модель: `Track`, `Lyrics`, `Playlist`, `Profile`, `Settings`, `SessionState`, `PersistedDb`, `IpcResult`. |
| `ipc.ts` | Константы каналов `CH`, события `EV`, тип `MediaCommand`. Единственное место, где перечислены имена каналов. |
| `defaults.ts` | `DEFAULT_SETTINGS`, `DEFAULT_FORMAT_PRIORITY`, `formatRank()`, `DEFAULT_SESSION`, `createDefaultDb()`, `createDefaultRegistry()`, `formatTime()`, `makeId()`, `safeFileName()`. |
| `lrc.ts` | Единственная реализация разбора и сериализации LRC. |
| `tracklist.ts` | Разбор и экспорт списков треков, нормализация для сопоставления. Покрыт юнит-проверками. |
| `fileNames.ts` | Восстановление символов, запрещённых в именах файлов Windows. Покрыт юнит-проверками. |

Правило: `src/shared` компилируется и в Node, и в браузер, поэтому здесь нет `node:*`,
`electron` и обращений к `window`.

## IPC

`src/shared/ipc.ts` объявляет каналы, `src/main/ipc.ts` их реализует, `src/preload/index.ts`
выставляет типизированный `window.kolaars`. Каждый обработчик возвращает конверт
`IpcResult<T> = { ok: true, data } | { ok: false, error }`; мост разворачивает его, превращая
ошибку в исключение, поэтому интерфейс пользуется обычным `try/catch`.

Направления:

- **renderer → main**: `ipcRenderer.invoke` — загрузка документа, работа с плейлистами,
  текстами, провайдерами, файлами и загрузками.
- **main → renderer**: `webContents.send` по событиям `EV` — состояние окна, прогресс
  загрузок и импорта, медиа-команды из меню и системных клавиш.

Меню приложения (`src/main/menu.ts`) не выполняет действия само: оно отправляет
`MediaCommand`, а интерфейс решает, что с ним делать. Так одна и та же логика работает и для
меню, и для горячих клавиш, и для медиа-клавиш Windows.

## Хранение (`db.ts`)

Один документ `kolaars.json` **на профиль**, внутри `userData/profiles/<id>/`:

- чтение при старте, слияние с текущими значениями по умолчанию (`migrate()`), поэтому старый
  файл после обновления не ломается;
- изменения — через `updateDb(fn)`, запись откладывается на 400 мс (debounce) и сериализуется
  в цепочку промисов, чтобы конкурентные записи не перемешивались;
- сама запись атомарна: сначала `kolaars.json.tmp`, затем `rename`;
- при выходе `flushAndClose()` дописывает документ;
- повреждённый файл не перезаписывается, а переименовывается в `kolaars.json.corrupt-<время>`.

Рядом живут `downloads/` (офлайн-аудио) и `covers/` (вырезанные обложки) — то есть профиль
переносится копированием одной папки.

### Профили

`userData/profiles.json` — реестр: список профилей и идентификатор активного. Каталог данных
от версии без профилей переносится в профиль `default` («Основной») при первом запуске
(`adoptLegacyFiles()`), поэтому существующая библиотека не теряется.

Смена профиля (`setActiveProfile()`): сначала `flushAndClose()`, затем подмена каталога,
сброс кэша документа и повторная загрузка. Идентификаторы профилей годятся в имена каталогов
и проверяются регулярным выражением — обход пути через IPC невозможен.

Вместе с профилем сбрасываются записи офлайн-загрузок (`forgetDownloads()`) и переподключаются
файлы нового профиля (`restoreDownloads()`), а интерфейс получает событие и заново выполняет
`bootstrap()`.

## Импорт списка треков (`importList.ts`)

Разбор вставленного текста живёт в `shared/tracklist.ts` — чистом, доступном обоим процессам
модуле без зависимостей, поэтому он покрыт юнит-проверками (`npm run test:tracklist`).
Понимает строки «Исполнитель — Название» с любым из типовых разделителей, CSV/TSV с
заголовком (порядок колонок определяется по заголовку), `#EXTINF` из M3U и пути к файлам.

Сопоставление выполняет главный процесс, в три шага:

1. **библиотека** — нормализованный ключ «исполнитель+название» (диакритика, регистр,
   пунктуация и скобочные уточнения отбрасываются);
2. **открытый архив** — поиск в Internet Archive, но результат принимается только если
   название действительно совпало, иначе к строке привязался бы случайный трек;
3. **только название** — если звука нет нигде, строка сохраняется как трек с
   `source: 'list'` и пустым `streamUrl`. Идентификатор детерминированный
   (`list:<sha1>`), поэтому повторный импорт не создаёт дубликатов.

Тексты запрашиваются отдельным проходом у LRCLIB (`lrclibGet`, затем `lrclibSearch`). Вся
запись в документ выполняется **одним** `updateDb()`, поэтому медленный поиск не оставляет
профиль полуимпортированным. Параллелизм ограничен (`CONCURRENCY = 3`).

## Импорт локальных файлов (`localFiles.ts`)

Обычный случай — файл с тегами: `music-metadata` отдаёт исполнителя, название, альбом, год,
жанр, длительность и встроенную обложку (она один раз выгружается в каталог `covers` и дальше
отдаётся по `kmedia://`). Рядом лежащий `.lrc` подхватывается автоматически.

Выгрузка из музыкальных сервисов выглядит иначе, и на это есть четыре послабления:

- **имя файла как источник имён.** Если тегов нет, имя разбирается тем же `parseArtistTitle`
  из `shared/tracklist.ts`, что и строки списка: `Исполнитель - Название` → исполнитель
  `Исполнитель`, название `Название`. Тег всегда важнее имени, имя только заполняет пропуски;
- **запрещённые символы** (`shared/fileNames.ts`). Windows не хранит `\ / : * ? " < > |`, и
  сервисы подменяют их подчёркиванием. `restoreForbiddenCharacters()` возвращает наиболее
  вероятный символ только там, где подсказка однозначна: `_` в самом конце → `?`
  (`Что ты знаешь_` → `Что ты знаешь?`), `_` перед пробелом → `:` (`Часть 1_ Начало`),
  `_` между буквами → `/` (`AC_DC`). Серия подчёркиваний (`hate music ^__`), ведущее
  подчёркивание и `_` между пробелами остаются как есть — неверная догадка хуже видимого
  подчёркивания. Функция применяется к имени, исполнителю и названию, то есть ко всему, что
  берётся из файловой системы; значения из тегов не трогаются, их никто не подменял;
- **обложка отдельным файлом** (`sidecarCover.ts`). Ищется картинка рядом с треком по
  нескольким соглашениям, от самого точного к общему: `Трек.flac.cover.jpg` (так пишет
  Яндекс Музыка), `Трек.flac.jpg`, `Трек.cover.jpg`, `Трек.jpg`, `cover.jpg` и `folder.jpg`.
  Поиск не зависит от регистра, каталоги и пустые файлы не принимаются. Файл не
  копируется — он открывается по `kmedia://` там, где лежит. Имя картинки сравнивается с
  именем файла на диске, поэтому восстановление символов здесь не нужно: обе стороны
  подменены одинаково;
- **длительность из декодера.** Контейнеры, которых не понимает `music-metadata`
  (например, FLAC внутри MP4 — так выглядят «`.flac`» из выгрузки), просто не дают
  длительности. Chromium такие файлы играет, поэтому при первом воспроизведении плеер
  сохраняет длительность, полученную от медиаэлемента (`rememberTrackDuration`), и список
  перестаёт показывать пустое место.

Одна и та же песня в такой папке обычно лежит в нескольких форматах сразу. Ключ песни —
имя файла без расширения: именно оно остаётся неизменным при смене формата. Список файлов
сортируется по приоритету форматов (`settings.formatPriority`, по умолчанию без потерь
впереди), поэтому первым в библиотеку попадает лучший вариант, а остальные возвращаются в
поле `duplicates` и в библиотеку не добавляются — но и не удаляются с диска. Файлы, уже
лежащие в библиотеке, заранее занимают свои ключи, так что повторный импорт папки ничего не
меняет, а появившийся позднее формат не подменяет уже добавленный трек: подмена сломала бы
ссылки в плейлистах и избранном.

Логика поиска обложки не тянет за собой Electron, поэтому проверяется отдельно
(`npm run test:covers`) на настоящих файлах во временном каталоге; восстановление символов
проверяется так же (`npm run test:names`).

## Медиа-протокол `kmedia://`

Интерфейсу не выдаётся доступ к `file://`. Вместо этого главный процесс регистрирует
привилегированную схему (`media.ts`):

1. файл, который нужно воспроизвести, регистрируется через `allowMediaPath()` или
   `allowMediaRoot()`;
2. интерфейс получает `kmedia://local/<base64url пути>`;
3. обработчик схемы проверяет путь по нормализованному списку разрешённых и отдаёт файл
   потоком, разбирая `Range`-заголовок вручную (`byteRange.ts`) и отвечая `206 Partial
   Content` с `Content-Range` и `Accept-Ranges: bytes`.

Шаг 3 важен именно тем, что делается вручную. `net.fetch` на `file://` выглядит проще, но
игнорирует `Range` и не сообщает `Accept-Ranges`, поэтому медиаэлемент считал поток
не подлежащим перемотке: полоса перемотки не двигала трек, а переход к строке текста или к
сохранённой позиции начинал песню заново. Теперь `audio.seekable` покрывает весь файл.

Схема объявляется до `app.whenReady()` (`registerMediaScheme`) и устанавливается после
(`registerMediaProtocol`).

Список разрешённых существует только в памяти процесса. Чтобы после перезапуска библиотека не
осталась с пустыми обложками и нерабочим воспроизведением, `loadDb()` при каждом чтении профиля
заново разрешает то, на что ссылаются сохранённые треки (`allowMediaPathsOfTracks`) — звуковой
файл и картинку рядом с ним.

## Безопасность

- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`;
- в окне нет Node — только `window.kolaars`;
- переходы по внешним ссылкам открываются системным браузером, навигация окна ограничена;
- CSP применяется и к собранному приложению: `script-src 'self'`, `object-src 'none'`,
  `frame-ancestors 'none'`, изображения и медиа — с `kmedia:`, `blob:` и `https:`;
- единственный экземпляр приложения (`requestSingleInstanceLock`).

## Состояние интерфейса

Три хранилища `zustand` в `src/renderer/src/state`:

| Файл | Ответственность |
| --- | --- |
| `store.ts` | Маршрут, каталог и его индекс, плейлисты, избранное, настройки, очередь, панели, тосты. Загружает документ при старте (`bootstrap`) и разрешает идентификаторы (`resolveTracks`). |
| `player.ts` | Движок воспроизведения: элемент `<audio>`, очередь, повтор, перемешивание, громкость, восстановление сессии. |
| `lyrics.ts` | Тексты: поиск по встроенному сборнику, онлайн-поиск, сохранение, черновики мастерской. |

Ключевое правило: **списки хранят только идентификаторы**. Плейлисты, избранное, очередь и
сессия ссылаются на треки по `id`, а сами треки лежат в словаре `tracks` документа и в
встроенном каталоге. Всё разрешение сосредоточено в `resolveTracks(ids)`: он отбрасывает
идентификаторы `arc:…`, которых нет в индексе, запрашивает их у Internet Archive и
кэширует результат. Благодаря этому документ не растёт от размера библиотеки, а треки,
найденные онлайн, «оживают» после перезапуска.

## Встроенные данные

- `data/seed-catalog.json` — 211 треков и 10 подборок. Собирается из живых запросов Internet
  Archive (`scripts/build-seed-catalog.mjs`), читается главным процессом из
  `process.resourcesPath` в собранном приложении.
- `data/lyrics-pack.json` — 65 песен общественного достояния. Импортируется прямо в бандл
  главного процесса (`src/main/lyrics/pack.ts`), поэтому не требует файлового доступа.

## Сборка

`electron-vite` собирает три конфигурации независимо (см. `electron.vite.config.ts`):

| Процесс | Формат | Результат | Особенности |
| --- | --- | --- | --- |
| main | CommonJS | `out/main/index.js` | `externalizeDepsPlugin`, псевдоним `@shared` |
| preload | CommonJS | `out/preload/index.js` | без Node-зависимостей, кроме `electron` |
| renderer | ESM | `out/renderer/` | React 19, псевдонимы `@` и `@shared` |

`music-metadata` — ESM-пакет, а главный процесс — CommonJS, поэтому он загружается
динамическим `import()` и вынесен из asar (`asarUnpack`).

Упаковка — `electron-builder`: NSIS-установщик и портативная сборка для Windows x64.
`electronDist` указывает на `node_modules/electron/dist`, а `downloadAlternateFFmpeg`
выключен, поэтому упаковка не требует загрузок с GitHub. Инструменты правки ресурсов и сборки
установщика (rcedit, 7-Zip, NSIS) кэшируются скриптом `scripts/fetch-builder-tools.mjs`,
который запускается автоматически перед каждой командой упаковки и проверяет каждый архив по
SHA-256.
